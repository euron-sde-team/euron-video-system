# ADR-0003: AES-128 HLS with KMS envelope encryption now, multi-DRM later

- **Status:** Accepted
- **Date:** 2026-10-22

## Context

Content must not be watchable by anyone who has not been authorized by the
integrating platform. Options range from signed URLs only, through clear-key
encryption (AES-128 HLS, ClearKey CENC), to hardware-backed DRM (Widevine L1,
FairPlay, PlayReady SL3000).

Hardware DRM needs licensing agreements, a license server per system, cbcs
CMAF packaging, and per-platform player integration. That is a large surface
to take on before the rest of the platform exists.

## Decision

Ship **AES-128 HLS** (`#EXT-X-KEY:METHOD=AES-128`) as the protection mode, with:

1. **One random 128-bit key per video** from the OS CSPRNG, generated by the
   worker at packaging time.
2. **Envelope encryption at rest:** the key is wrapped by a KMS customer
   managed key with `EncryptionContext = {videoId}`, and only the ciphertext is
   stored. Without KMS (local development) it is wrapped with AES-256-GCM,
   using a key derived via HKDF and the video id as additional authenticated data.
3. **Tokenized key delivery:** the key is served only by the API, only to a
   holder of a valid, unexpired, unrevoked playback token bound to that video,
   with `Cache-Control: no-store`.
4. **Tokenized playlists:** the token lives in the playlist URLs (native Safari
   cannot attach headers), so playlists are rewritten per request and never cached.
5. **Signed segment delivery:** segments come from a private bucket through
   short-lived signed URLs. They are encrypted anyway; signing stops hotlinking
   and bulk scraping.
6. **Deterrence layers:** a dynamic on-screen watermark carrying the viewer's
   identity, per-viewer concurrent-session limits, and instant session revocation.

The schema reserves `protection_mode = 'drm_cbcs'` and the packaging stage is
isolated, so multi-DRM can be added without migrating existing videos.

## Consequences

**What this protects against:** unauthenticated access, link sharing (tokens
expire, sessions are capped and revocable), hotlinking, storage-bucket leaks
(objects are encrypted and keys are not in storage), and database leaks (keys
are wrapped by KMS).

**What it does not protect against:** a *legitimately authorized* viewer
extracting the key for a video they are allowed to watch, and recording the
screen. Clear-key schemes cannot prevent the first. Only hardware-backed DRM
can, and nothing fully prevents the second. We say this plainly in
[security.md](../security.md) rather than calling AES-128 "DRM".

## Roadmap

`drm_cbcs`: CMAF cbcs packaging (Shaka Packager), Widevine and FairPlay license
proxying through the same playback-session authorization, PlayReady optional.
Forensic A/B watermarking (`watermark_mode = 'forensic_ab'`) to trace leaks
back to a session.
